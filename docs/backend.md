# Backend

The backend is one Java 21 Spring Boot application. [Architecture](architecture.md) describes its runtime placement; [security](security.md) and [database](database.md) describe the controls around its operations.

## Package responsibilities

Packages live under [io.github.panteliszara.issunexa](../backend/src/main/java/io/github/panteliszara/issunexa/):

| Package | Responsibility |
| --- | --- |
| `auth.api` | CSRF, login, session and logout REST endpoints |
| `user` | Persisted accounts, normalized email, password hashing and role data |
| `ticket` / `ticket.api` | Ticket entity rules, querying, ownership, self-claim, status changes and DTO contracts |
| `ticket.comment` | Visible-Ticket checks, append-only comments and comment pagination |
| `ticket.history` | Structured lifecycle entries and authorized history reads |
| `shared.security` | Authentication provider, session/CSRF strategies, filter rules and security errors |
| `shared.web` / `shared.openapi` | Problem Details mapping and generated API documentation configuration |

These packages call each other in-process. For example, comment/history services reuse Ticket visibility checks, and Ticket mutations write lifecycle entries through the history repository.

## Request and transaction boundaries

1. Spring Security handles authentication and CSRF checks before the controller.
2. Controllers bind and validate request DTOs/parameters and pass the authenticated principal's email to services.
3. Services resolve persisted accounts, enforce visibility/role rules and coordinate repository operations in transactions.
4. Controllers map results into explicit response records rather than exposing JPA entities.

[TicketController](../backend/src/main/java/io/github/panteliszara/issunexa/ticket/api/TicketController.java), [TicketService](../backend/src/main/java/io/github/panteliszara/issunexa/ticket/TicketService.java) and [TicketResponse](../backend/src/main/java/io/github/panteliszara/issunexa/ticket/api/TicketResponse.java) show this path. Response contracts expose the fields needed by the UI; the JPA version and requester entity are not included in the Ticket response. Open EntityManager in View is disabled in [configuration](../backend/src/main/resources/application.yml); repository fetch plans must supply associations needed by responses.

Creation derives the requester from the principal and starts the Ticket at `OPEN`. Claiming assigns the authenticated staff account to an unassigned Ticket. The [Ticket entity](../backend/src/main/java/io/github/panteliszara/issunexa/ticket/Ticket.java) permits `OPEN → IN_PROGRESS`, `IN_PROGRESS → RESOLVED`, and `RESOLVED → IN_PROGRESS/CLOSED`; `CLOSED` is terminal. Invalid transitions, repeated claims and optimistic-lock conflicts produce `409` through [ApiExceptionHandler](../backend/src/main/java/io/github/panteliszara/issunexa/shared/web/ApiExceptionHandler.java).

Ticket creation, status changes and claims write history entries in the same service transaction as the Ticket change. [Comments](../backend/src/main/java/io/github/panteliszara/issunexa/ticket/comment/TicketCommentService.java) are separate from lifecycle history and do not change Ticket status or assignment. Neither comments nor history have update/delete endpoints.

## Query ownership

The backend owns visibility, filtering, sorting, pagination and totals. TicketService combines requester visibility and requested filters from [TicketSpecifications](../backend/src/main/java/io/github/panteliszara/issunexa/ticket/TicketSpecifications.java) before pagination; text search escapes `%`, `_` and backslash as literal characters. Sorting includes ID as a deterministic tie-breaker. Page parameters are zero-based, with a default size of 20 and maximum size of 100. The frontend displays these results without computing its own filtered totals.

This keeps authorization and query behavior consistent for browser and direct API callers. Services and repositories share one schema and transaction manager, so package boundaries remain coupled through domain relationships and persistence.

## Verification and API reference

From the repository root, with Java 21 and a Docker runtime accessible to Testcontainers:

```sh
cd backend
./mvnw --batch-mode --no-transfer-progress verify
```

The [Maven build](../backend/pom.xml) includes unit/MVC tests and PostgreSQL integration tests. Docker image construction is a separate build path and does not substitute for this verification. The [README](../README.md#ticket-api) provides endpoint examples; OpenAPI JSON and Swagger UI are generated by the running backend.
